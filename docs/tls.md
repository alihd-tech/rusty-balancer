# TLS and certificate management (P3)

TLS is opt-in and HTTP-only P0–P2 configurations remain valid. The existing listen address serves HTTP, while tls.listen is the separate TLS 1.2/1.3 listener. ALPN negotiates HTTP/2 or HTTP/1.1.

## Manual certificates

Use configs/tls.example.toml as a starting point. Generate local development keys with OpenSSL, never commit them:

```sh
mkdir -p certs
chmod 700 certs
umask 077
openssl req -x509 -newkey rsa:2048 -nodes -days 7 \
  -subj '/CN=localhost' -addext 'subjectAltName=DNS:localhost' \
  -keyout certs/localhost.key -out certs/localhost.crt
cargo run -- --config configs/tls.example.toml validate
cargo run -- --config configs/tls.example.toml serve
curl --cacert certs/localhost.crt https://localhost:8443/
```

Repeat the [[tls.certificates]] table for different certificates and exact DNS names. The PEM file must contain the leaf first, then intermediates. Keys and named certificates are checked on startup and by validate. Unknown SNI is rejected. Certificate replacement in manual mode requires restarting the process. No wildcard matching or no-SNI default certificate is implemented.

## Native ACME

The separate ACME mode manages account registration, certificate orders, TLS-ALPN-01 validation, cached keys, and renewal via rustls-acme. Configure a single SAN certificate covering the explicitly listed domains in tls.acme.domains. Manual and ACME modes are mutually exclusive for this milestone. Use a staging directory first and switch to production only after validation succeeds; switch to a separate private production cache directory at the same time.

- Point each configured public DNS name to the server, including relevant IPv6 records.
- Public TCP 443 must reach the Rusty Balancer TLS listener (directly or through TCP forwarding, not a TLS-terminating CDN). The example uses loopback and must be adapted for real deployment. Do not start a public deployment before hardening.
- Run as a dedicated user and persist the state directory; on Unix its permissions must be 0700. Keep it out of public static roots and backups that lack encryption.
- Until the first certificate is issued, normal TLS handshakes can fail. The certificate state machine manages renewal/retry. No on-demand certificate issuance or DNS-01 is available.
- Config validation does not contact Let's Encrypt or issue certificates.

## Redirect policy

tls.redirect_http = true enables 308 redirects. Only explicitly configured certificate names can be redirected; unknown or missing hosts receive 421. The original path and query are retained, and the destination port comes from tls.public_port or tls.listen, not a client-provided port. For ACME, public_port must be 443. When redirect is off, HTTP continues to serve normal routes. HTTPS request hosts must be on the TLS allowlist; this is not a per-connection SNI-to-Host equality check.

## HTTPS upstreams

HTTP and HTTPS origins can coexist in a pool. HTTPS uses Hyper with Rustls, Mozilla WebPKI roots and normal hostname and certificate verification. Health checks use the same connector. No insecure verification bypass, custom CA configuration, mTLS, or HTTP/2 upstream support is present yet. X-Forwarded-Proto is generated by the actual listener, not by incoming proxy headers.

## Verification

Run scripts/check.sh and scripts/tls-smoke.sh from the repository root. The smoke test generates a temporary development certificate, verifies a real HTTPS request, checks the redirect and verifies rejection of unknown SNI. Live ACME issuance requires a controlled domain and public TCP 443; it is not attempted during unit tests.
